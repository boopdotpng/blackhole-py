# Tensix lowering IR

Status: design draft

This is a small, tinygrad-like semantic IR for Tensix kernels.

Kernel authors describe values and computation. They do not choose NoC packets,
L1 staging, circular buffers, unpack, FPU versus SFPU, Dst layout, pack,
semaphores, or stalls. Those are lowering decisions.

The first implementation lives in `blackhole-py`, with the lowering logic kept
portable to `tinygrad/codegen/tensix.py`.

## 1. One staged UOp graph

Kernel authors build this public graph:

```python
@dataclass(frozen=True)
class UOp:
    op: Ops
    dtype: DType | None
    src: tuple["UOp", ...]
    arg: object = None
```

`src` means semantic value/effect dependencies. `arg` contains static metadata
such as an ALU opcode, reduction axes, or parameter description.

Example:

```python
x_buffer = UOp.buffer(slot=0, size=2000, dtype=DType.BF16)
out_buffer = UOp.buffer(slot=1, size=2000, dtype=DType.BF16)
x = x_buffer.index(shape=(1000,))
two = UOp.const(2.0, dtype=DType.F32)
y = x.alu(ALUOp.MUL, two)
done = y.move(out_buffer.index(shape=(1000,)))
root = UOp.sink(done)
```

There is no FPU, SFPU, unpack, or pack operation in the authored graph. Like
tinygrad, immutable `graph_rewrite` passes return new `SINK` roots using the
same `UOp` class. Later passes replace semantic nodes with compiler-generated
`INS` nodes tagged with a firmware role. There is no separate machine-graph
class.

Generated instruction payloads may describe operations such as:

```text
NOC_READ_EXACT
CB_RESERVE / CB_PUSH / CB_WAIT / CB_POP
UNPACK_RM_VECTOR / UNPACK_RM_ELW / UNPACK_RM_MVMUL
FPU_ELW / FPU_MVMUL / FPU_REDUCE
SFPU_ALU / SFPU_REDUCE
DST_REUSE_SRCA / DST_REUSE_SRCB
PACK_RM_EXACT
NOC_WRITE_EXACT
```

These are compiler-internal instructions. Unpack operations are generated by the
selected compute implementation's operand contract; they are not independently
selected from an indexed memory source. Generated instructions carry engine,
RISC, fragment, and resource dependencies and lower to the existing TTK
mechanisms.

```text
tinygrad or hand-built semantic graph
  -> choose core work partition
  -> lower indexes to exact row-major accesses
  -> choose FPU/SFPU paths and execution fragments
  -> allocate L1, CBs, Src, Dst, and LRegs
  -> generate resource dependencies and synchronization
  -> rewrite semantic nodes to role-tagged INS nodes
  -> priority topological sort
  -> split the stable order into five RISC streams
  -> encode
```

## 2. Semantic operation list

Keep the public op set small:

```python
class Ops(Enum):
    SINK = auto()

    BUFFER = auto()
    PARAM = auto()
    CONST = auto()
    RANGE = auto()
    INDEX = auto()
    MOVE = auto()

    ALU = auto()
    REDUCE = auto()
    MATMUL = auto()
```

`MATMUL` is explicit for now. The graph author states the matrix operation and
the lowerer selects MVMUL or another implementation; it does not have to
recognize an indexed multiply/reduce pattern first. It initially accepts rank-1
and rank-2 operands (dot, matrix-vector, vector-matrix, and matrix-matrix) plus
optional transpose flags. Its result is always FP32 accumulator data.

### Ops and direct dependencies

| Op | Direct `src` dependencies | Produces | `arg` |
|---|---|---|---|
| `BUFFER` | none | runtime-bound storage object | argument slot, exact byte size, element dtype |
| `PARAM` | none | runtime scalar | slot, dtype |
| `CONST` | none | scalar constant | value |
| `RANGE` | scalar start, end, and step | logical loop index | logical axis |
| `INDEX` | buffer, scalar element offset, optional validity predicate | lazy logical memory view/span | shape and element strides |
| `MOVE` | source value/view and destination view | destination effect | none |
| `ALU` | one or two values | logical result | add/sub/mul/div/max/neg/exp/reciprocal/rsqrt |
| `REDUCE` | one value | reduced result | sum/max/product and logical axes |
| `MATMUL` | left and right values/views | FP32 dot, vector, or matrix result | optional left/right transpose flags |
| `SINK` | all required `MOVE`s and effects | nothing | none |

`RANGE` replaces hand-authored repeat constructs. It describes logical
iteration and can feed index arithmetic. It does not request a Tensix MOP.

The same `Ops` enum also has staged compiler ops that kernel authors do not
construct:

| Op | Meaning |
|---|---|
| `INS` | generated instruction payload plus a BRISC/NCRISC/TRISC role |
| `LINEAR` | final dependency-ordered `INS` sequence for one role |
| `PROGRAM` | the five `LINEAR` role streams |

`INDEX` is lazy: it describes values in storage but does not prescribe how they
reach an engine. An `ALU`, `REDUCE`, or `MATMUL` may consume an `INDEX`
directly. Its
selected compute plan realizes the operand through the required NoC, staging,
and unpack sequence.

`BUFFER` replaces the Python `Buffer` object in the semantic graph:

```python
@dataclass(frozen=True)
class BufferArg:
    slot: int       # runtime-argument slot containing the base address
    size: int       # exact valid bytes
    dtype: DType
```

Shape, strides, views, and validity belong to `INDEX`, not `BUFFER`. Bank
count, DRAM endpoints, stripe size, and NoC topology belong to the target. This
keeps a buffer equal to a typed runtime storage argument. At launch, the host
writes the allocation's base address into `slot`. Each generated RISC stream
loads that base from the runtime-argument table when it needs the buffer.
`BUFFER` and `PARAM` use the same slot namespace; the difference is that a
`BUFFER` slot is interpreted as a base address with compile-time size/dtype
metadata. Repeated uses should share one hoisted slot load per RISC stream.

The slot value may use the target's encoded-base convention when bank rotation
or placement bits are required. The kernel image remains reusable with another
allocation by rebinding the same slot.

`MOVE(src, dst)` is the one explicit materialization/copy operation:

- computed value to buffer view: store the result, converting to the
  destination buffer dtype when required;
- buffer view to buffer view: direct copy when dtypes match, otherwise a
  generated conversion;
- value/view to a required logical destination: preserve a copy or handoff
  required by the graph.

The semantic destination is never a raw SrcA, SrcB, Dst, CB, or LReg. Those
physical endpoints exist only in the scheduled machine IR.

Indexes may be static or depend on runtime parameters, loop variables, or the
logical core rank.

Every value also records its logical shape, dtype, and validity predicate.
Physical fragments and inactive hardware lanes are introduced later.

There is no public `CAST` op. Integer and non-FPU operations follow their
ordinary promotion rules. Every operation selected for the FPU produces FP32
Dst/accumulator state, regardless of its input buffer dtypes. `MOVE` enforces
the destination `BUFFER` dtype and is therefore the normal narrowing/rounding
boundary. The lowerer inserts any required conversion and may fuse it into
unpack or pack.

For example, adding two BF16 buffers into an FP32 buffer needs only:

```python
value = a.index(shape=shape).alu(ALUOp.ADD, b.index(shape=shape))
done = value.move(fp32_output.index(shape=shape))
root = UOp.sink(done)
```

The FPU computes the add in FP32 Dst and `MOVE` materializes FP32 directly; the
caller does not add a cast node. If the destination were BF16, `MOVE` would
perform the BF16 rounding while packing.

## 3. Parameters and indexing

Use UOps for values that participate in expressions rather than hiding them in
ad-hoc op arguments.

Runtime scalar parameters include:

- dynamic shapes and strides when required;
- token/cache position;
- logical core rank or per-core work descriptors.

Buffer slots, sizes, and dtypes are `BUFFER` arguments. Actual buffer base
addresses and scalar `PARAM` values are supplied through the runtime-argument
table. Other static choices remain in `arg`.

For example, a row-major matrix access is logically:

```text
weight: BUFFER(slot, size=M*K*2, dtype=BF16)
row:    scalar expression
k:      scalar expression

INDEX(weight, row*K + k, shape=(M,K), strides=(K,1),
      valid=(row<M and k<K))
```

The movement lowerer coalesces adjacent indexes into exact byte spans. It may
split a span at DRAM stripes or NoC packet limits, but may not read an invalid
element. Static index terms are known while lowering, so it can precompute
constant byte offsets and the corresponding bank/endpoint pattern. The runtime
base comes from the buffer's argument slot; dynamic index terms become only the
remaining kernel arithmetic.

Compute ops do not carry global addresses. `ALU(mul)` consumes logical values
or indexed storage views; only `BUFFER`/`INDEX`/`MOVE` describe persistent
storage. After an engine path is selected, that compute plan defines how its
row-major inputs must be unpacked from L1 into SrcA, SrcB, Dst, or SFPU-visible
state.

## 4. Core assignment

Do not tag every semantic UOp with a physical core.

Core assignment belongs to the kernel launch and work partition:

```python
@dataclass(frozen=True)
class LaunchSpec:
    cores: tuple[tuple[int, int], ...]
    partition: WorkPartition

@dataclass(frozen=True)
class CoreBinding:
    rank: int                    # logical rank in this launch
    coordinate: tuple[int, int]  # physical worker coordinate
    work: dict[str, int]         # row_start, row_count, head, ...
```

One semantic graph plus one `LaunchSpec` lowers to one `TTProgram` containing
the images and parameter data for every participating core.

Every op executes on the current core selected by the launch. Physical
coordinates are launch metadata; arithmetic nodes never mention `(x, y)`.
There is no cross-core communication op in the initial semantic IR. Work must
be independently partitionable, or placed in a separate kernel launch.

Initial partition policies can be explicit:

| Kernel pattern | Partition |
|---|---|
| elementwise | contiguous output element ranges |
| GEMV/matmul | contiguous output rows; each core owns the full local reduction |
| attention | one KV head and its query-head group per core |
| small kernel | one core |

For `N` output rows over `C` cores, logical core `c` owns:

```text
start = floor(c       * N / C)
end   = floor((c + 1) * N / C)
```

This produces exact ragged ranges without padded per-core tensors.

The first lowerer may specialize one graph per distinct core class. For
example, a 26-row and a 27-row projection image can be compiled separately and
assigned to the matching cores. Once dynamic five-stream loops are verified,
one shared image can instead read `row_start` and `row_count` from its per-core
parameter table.

## 5. Lowering policy

Core partitioning happens before engine selection because each core's local
shape determines its full blocks and tails.

Each selected compute implementation is a small plan:

```python
@dataclass(frozen=True)
class ComputePlan:
    input_fragments: tuple[FragmentRequirement, ...]
    output_fragment: FragmentLayout
    issues: tuple[MachineOp, ...]
```

Pattern matchers replace semantic operations with role-tagged `INS` nodes.
After all rewrites, one priority topological sort is filtered into the five
role streams while preserving their relative order.

### RANGE versus MOP

`RANGE` is a logical program loop. MOP is a target instruction-compression and
engine-control detail. They must not map one-to-one.

The lowerer first chooses the exact unpack, compute, and pack implementations
and their fragment shapes. Those implementations then generate their own
known-safe MOP/Replay templates. The existing `ttk.unpack.Unpack`,
`ttk.fpu.Fpu`, and `ttk.pack.Pack` methods already follow this model: callers
request a move, matmul, reduction, or pack, and the TTK implementation selects
and configures the corresponding MOP internally.

If a logical `RANGE` surrounds several tiles, the RISC loop iterates tiles;
each selected engine operation may use a private MOP for faces or matrix
products inside that iteration. Awkward tails select masked or smaller plans.
They never require a kernel author to supply MOP words.

FPU plans have one non-negotiable invariant:

```text
FPU output fragment = FP32 Dst accumulator
```

There is no BF16 FPU Dst mode in generated kernels. FPU-to-FPU Dst reuse and
FPU-to-SFPU handoff preserve FP32. Conversion to BF16 happens only when a
`MOVE` materializes into a BF16 buffer. This avoids losing precision between
fused operations and throughout reductions/MVMUL accumulation.

For example, an FPU multiply plan requires an `8x16` SrcA fragment and an
`8x16` SrcB fragment, so it generates the matching row-major unpack operations
before `FPU_ELW`. An SFPU multiply plan requires an SFPU-visible Dst footprint
and LRegs, so it generates that staging/load sequence instead. If a producer is
already in a compatible Dst fragment, the plan may generate Dst reuse rather
than an L1 round trip.

### Memory

When a compute op consumes `INDEX(...)`, operand realization lowers to:

```text
address calculation
-> exact NoC span(s)
-> private L1 or CB staging
-> generated completion/credit protocol
```

The consuming `ComputePlan` then adds the required unpack or reuse operation.
This keeps memory addressing separate from engine fragment formation while
allowing them to be scheduled and fused together.

`MOVE(value, INDEX(...))` lowers to:

```text
value in Dst/SFPU state
-> exact row-major pack into private L1/CB
-> exact NoC span(s)
-> generated completion/credit protocol
```

Pack alignment padding may exist in private L1 scratch. `NOC_WRITE_EXACT`
writes only the logical byte count.

### Engine selection

The lowerer selects an implementation from the operation and local shape:

| Semantic pattern | Initial lowering policy |
|---|---|
| arbitrary elementwise values | SFPU in groups of up to 32 |
| compatible 128-value add/multiply | FPU `8x16` elementwise block |
| `MATMUL` with a compatible matrix panel | FPU `8x16 @ 16x16` MVMUL |
| wide sum/max | FPU reduction when proven; SFPU fallback |
| exp, reciprocal, reciprocal square root | SFPU |
| cheap FPU op after SFPU | SFPU store to Dst, then Dst reuse into FPU source |

This policy may change without changing the semantic graph.

For `x.alu(ALUOp.MUL, 2.0)`, the same graph can become:

```text
small/tail path:
  NoC read -> row-major SFPU fragment -> SFP multiply -> exact pack/write

wide path:
  NoC read -> row-major SrcA/SrcB fragment -> FPU ELWMUL -> exact pack/write
```

The choice is made for each full block and tail, not once for the entire tensor.

### Matmul and GEMV

Given a `MATMUL(left, right)`, the lowerer chooses between:

- FPU elementwise multiply plus FPU/SFPU reduction;
- FPU MVMUL panels;
- the SFPU correctness fallback.

The semantic graph supplies operand shapes, index relationships, dtypes,
validity, and transpose flags. The selected machine op supplies panel
coordinates, accumulate behavior, and `live_m/live_n/live_k`.

## 6. Tails and row-major storage

Global and inter-kernel buffers are always exact dense row-major bytes:

```text
size = product(shape) * dtype.itemsize
```

There is no tilized flag or padded shard in the semantic IR.

Tails are handled at three separate boundaries:

| Boundary | Tail rule |
|---|---|
| global memory | issue exact valid byte spans only |
| execution fragment | track `live_shape`; fill inactive reduction lanes with the identity |
| output pack | stage an aligned private flush, then write exact valid bytes |

Initial identities are:

| Reduction | Inactive value |
|---|---:|
| sum or matmul K | `0` |
| max | `-inf` |
| product | `1` |

Examples:

- elementwise tail: SFPU predicate for 1 through 31 live lanes;
- FPU elementwise tail: use a full locally filled fragment when profitable,
  otherwise lower the tail to SFPU;
- MVMUL edge: record `live_m/live_n/live_k`, fill invalid K positions with
  zero, and never pack invalid M/N positions;
- ragged core shard: loop over exactly `row_count`, then write
  `[row_start:row_start+row_count]`.

Irregular indexes initially lower through compiler-owned L1 gather/scatter.
Later passes may recognize strided unpack or more efficient NoC patterns.

## 7. Scheduled resources and roles

After engine selection, the machine graph records locations and fragments such
as:

```text
L1_RM_SPAN
SFPU_4X8
FPU_ELW_8X16
FPU_MVMUL_A_16X16
FPU_MVMUL_B_8X16
DST_8X16
DST_SCALAR
PACKED_RM_SPAN
```

Normal role assignment is:

| Machine operation | Role |
|---|---|
| NoC read/write | BRISC or NCRISC |
| unpack and source formation | TRISC0 |
| FPU/SFPU | TRISC1 |
| pack | TRISC2 |

The protocol pass adds per-RISC order, CB capacity, NoC completion, source
validity, Dst ownership, engine serialization, configuration ownership, and
mutex dependencies.

Important resource states:

```text
SrcA/SrcB:
  CLEAR -> UNPACK_WRITING -> VALID -> MATH_READING -> CLEAR

Dst:
  FREE -> MATH_OWNED -> PUBLISHED -> PACK_OWNED -> FREE
```

The verifier rejects dependency cycles, finite-CB deadlocks, invalid fragment
transitions, unbalanced resources, and incomplete exit state before emission.

## 8. Lowering API and files

The standalone API should be approximately:

```python
program = lower_kernel(graph, launch_spec, target)

# program contains:
# - per-core parameters/work descriptors
# - core or core-class -> five scheduled streams
# - debug node map
# - resource manifest
```

Suggested `blackhole-py` modules:

```text
ttir/ops.py        semantic UOp/Ops and typed arguments
ttir/lowerer.py    partitioning, indexing, tails, and engine/path selection
ttir/machine.py    internal fragments and machine operations
ttir/protocol.py   allocation, resource edges, and synchronization
ttir/verify.py     graph checks and protocol simulation
ttir/emit.py       five streams through existing TTK/ISA APIs
```

In tinygrad, the equivalent entry point belongs in the existing
`tinygrad/codegen/tensix.py`. The renderer should only select and encode
already scheduled instructions.

## 9. Llama 3 mapping

The current non-row-major decoder already demonstrates the required work
partitions, but bakes them into hand-built `Program` variants and padded tiled
storage.

The row-major semantic graphs should use:

| Kernel | Core policy |
|---|---|
| embedding + first RMSNorm | one core |
| fused Q/K/V GEMV | output rows over 117 cores |
| RoPE + KV append + GQA | one KV head plus four Q heads over 8 cores |
| O/down projection | output rows over 117 cores |
| residual + RMSNorm | separate one-core kernel |
| gate/up GEMV + SwiGLU | matching gate/up rows over 117 cores |
| LM head | vocabulary rows over 117 cores |
| argmax | separate one-core kernel |

This removes padded compact Q/K/V, gate/up/hidden, and logits buffers; explicit
face-offset gather/scatter kernels; and the tiled KV-cache layout. FPU/SFPU
math sequences can be reused after their data movement and ownership are
expressed by the machine lowerer.

## 10. First milestone

Build one semantic identity or multiply graph and lower it without public
transport/unpack/pack/sync operations:

```text
semantic:
  INDEX -> ALU -> MOVE(result, output INDEX)

generated:
  exact NoC read -> unpack -> FPU or SFPU -> pack -> exact NoC write
```

Acceptance criteria:

- arbitrary logical sizes, including 1 through 129 elements;
- no read or write outside the exact buffer;
- correct SFPU and FPU path selection;
- all five streams and resources balance at exit;
- adjacent allocation canaries remain unchanged;
- generated diagnostics identify every cross-stream handoff.
