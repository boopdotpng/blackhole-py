About these docs

  • (probed) = measured on a p150 (the Tensix ones by the cfgprobe runs of 2026-11-23); the rest is from tt-isa-documentation or what ttrv kernels do every day. UNCERTAIN: marks what neither settles.
  • Tensix words are shown unrotated; a TRISC instruction stream stores each one rotated left by 2 (isa.inline / isa.outline).
  • Field layouts are tt-llk's. Several fields are wider than the bits the hardware reads (a Dst row is 10 bits, a Src row 6, an address-modifier slot 3); the field descriptions give the real widths.

Tensix instructions

MOP

opcode 0x01 · Control

Expand a macro-op template. The thread's MOP expander turns this one word into a looped sequence of instructions taken from the 9 MOP_CFG words (MMIO at 0xFFB80000, written by the RISC; isa.MOP_CFG_WORDS, in order outer, inner, start, end0, end1, loop0, loop1, last_inner, last).

Template 1, words (outer, inner, start, end0, end1, loop0, loop1, last_inner, last): repeat outer times { start; inner times { loop0; loop1 }; end0; end1 }, where the very last loop instruction of each outer pass is replaced by last_inner, and by last on the final pass. A slot holding NOP is skipped. loop1 present doubles the inner instruction count. Counts are 10 bits.

Template 0, words (-, flags, b, a0, a1, a2, a3, skip_a, skip_b): for i in 0..loop_count, if bit i of the 32-bit mask is clear emit a0 (then a1..a3 with flags bit 1) then b (with flags bit 0); if set emit skip_a then skip_b. The mask is MOP_CFG's 16 bits above this word's 16.

Wait for a load from 0xFFE80008 (returns once the expander is idle) before rewriting the template words. A template-1 MOP whose start slot is NOP with an inner count of 0 hits a hardware bug.

Template: 0 mask-driven, 1 nested loop.

Template 0: iterations minus 1.

mask_lo15:0int

Template 0: low 16 bits of the skip mask. Template 1: keep 0.

NOP

opcode 0x02 · Control

Tensix no-op. Does nothing. It is the filler for unused MOP template slots (the MOP expander skips a slot holding exactly this word) and the spacer after a config write whose next instruction would consume it. It is not a wait: use STALLWAIT to order units.

No arguments.

Configuration overview

  • A config write is not visible to the instruction immediately after it. Put one unrelated instruction (NOP) between a WRCFG / CFGSHIFTMASK and its consumer, and keep ttrv's two NOPs between a WRCFG of unpacker config and the UNPACR.

CFGSHIFTMASK

opcode 0xB8 · Configuration

Combine a scratch word into a Config word. Blackhole only. It modifies a Config word in the instruction stream with no RISC involved and no GPR, so a REPLAY or MOP body can step an address by itself: CFGSHIFTMASK(1, 3, 31, 0, 0, base word) is base += scratch[0]. With M = the low mask_width + 1 bits and r the rotation: word = (old, or old & ~rotr(M, r)) OP rotr(scratch & M, r). All 8 operations, both mask settings and the rotation match that in 96 of 96 random cases (probed).

2 cycles. Follow it with a NOP before an instruction that consumes the word. Probed recipe: a 14-instruction REPLAY body (reset Z, STALLWAIT, 4 UNPACR to SrcA, 4 to SrcB, STALLWAIT(Stall.CFG, Wait.UNPACK0), this instruction on the unpacker base, 2 NOPs) read 4 consecutive tiles correctly with no RISC involved.

Arguments

namebitstypedescription
keep_old23int

0 first clears the target bits the mask covers. 1 leaves the old value whole.

operation22:20int

How the value v is combined: 0 |= v, 1 &= v, 2 ^= v, 3 += v, 4 |= ~v, 5 &= ~v, 6 ^= ~v, 7 -= v.

mask_width19:15int

The value is the scratch word's low mask_width + 1 bits...

rotate14:10int

...rotated right by this many bits (the mask rotates with it).

scratch9:8int

Which scratch word: 0..2 are cfg.GLOBAL.scratch[0..2] from any thread, 3 is scratch[issuing thread]: word 209 + TRISC number (probed on all three).

word7:0int

Config word index. Never a scratch word.

Scalar unit overview

  • Each thread has 64 32-bit Tensix GPRs (MMIO at 0xFFE00000). These instructions compute in them, so a value such as an L1 address can be stepped and written to config (WRCFG) without the RISC.
  • They take 3 or 4 cycles. On Blackhole they do not hold back the thread's other units: STALLWAIT on Wait.THCON before another unit reads the result.

STOREIND

opcode 0x66 · Scalar unit

Store Tensix GPRs to L1, to MMIO, or into a Src bank. Three forms, chosen by word bits 23:21 (mmio, size, reg_size):

mmio=1                L1: writes at GPR[addr] * 16 + offset. (size, reg_size) picks the size: (0, 0) 128
                            bits from the four GPRs at data & 0x3C, (0, 1) 16 bits, (1, 0) 32 bits, (1, 1) 8 bits.
                            The ISA docs swap the 16-bit and 32-bit codes. Four back-to-back stores all landed
                            exactly. An UNPACR issued right after a store, with no STALLWAIT, reads the new
                            data (300 of 300); one issued before it reads the old data (probed).
mmio=0, size=1     MMIO (reg_size=0): writes the whole GPR at
                            0xFFB00000 + ((GPR[addr] + (offset >> 4)) & 0xFFFFC), so the offset's low 4 bits are
                            ignored (probed). Addresses below 0xFFB11000 are undefined.
mmio=0, size=0     Src: writes 4 BF16 datums, the halves of GPR[data & 0x3C] and the next GPR, into SrcA
                            (reg_size=0) or SrcB (reg_size=1) of the bank the unpacker owns. With
                            a = GPR[addr] + (offset >> 4): columns 4 * (a & 3) .. + 3, row a >> 2 for SrcB and
                            (a >> 2) - 4 for SrcA. Do not use it (probed, SrcA): the row and columns are as
                            stated, but the first of back-to-back stores is dropped and each low-half datum v
                            arrives as (v >> 8) | ((v & 0xFE) << 7). Only the high halves are exact.

Address counters overview

  • Each thread has three sets of address counters (ADCs): unpacker 0, unpacker 1 and the packer, picked by the counters field (isa.Adc: 1 unpacker 0, 2 unpacker 1, 4 packer). A set has two channels of X, Y, Z, W counters, each with a carry/reset copy (CR).
  • Channel 0 addresses the input (L1 for an unpacker, Dst for the packer) and channel 1 the output (Src or Dst for an unpacker, L1 for the packer). X on channel 0 is the first datum and X on channel 1 the last datum, inclusive, of the range an instruction moves: for an unpacker datums of the L1 tile, for the packer columns of each Dst row.
  • Nothing checks these counters. Three settings give wrong data with no error (probed): a packer channel-0 Y that is not a multiple of 4 packs fewer rows, a packer channel-1 X past 15 wraps mod 16 and shrinks every row, and an unpacker channel-1 X past x_dim - 1 reads on into the next tile and overwrites the start of Src.

INCADCXY

opcode 0x52 · Address counters

Increment X and Y counters. Adds each 3-bit value to its counter; the CR copies are not touched. Fields as SETADCXY, without a mask (0 leaves a counter alone). A change takes effect at the next new address.

Packer (probed): ch1_y += n moves the L1 output by n * l1_y_stride. ch0_x += k shifts the Dst read by k columns. ch0_y is the Dst row a PACR starts at, and a PACR reads from there to the end of its aligned 4-row group, rows Y .. Y | 3. So step ch0_y by 4 only: off a multiple of 4 each PACR reads 3, 2 or 1 rows, the address modifier's +4 keeps the misalignment, and a 16-PACR tile writes 48, 32 or 16 rows and leaves the rest empty.

Unpacker (probed with y_dim=1, x_dim=1024): ch0_y += 1 reads the next tile.

ADDRCRXY

opcode 0x53 · Address counters

Advance X and Y from their CR copies. For each counter whose mask bit is set: CR += value, then counter = CR. With a value of 0 it restores the counter from its CR copy, undoing INCADCXY steps and address-modifier increments. mask 0 does nothing. Fields as SETADCXY. Probed for all four counters.

Packer: ch0_x is the first Dst column read (it accumulates across tiles) and ch1_x the last, inclusive and mod 16. SETADCXX sets ch1_x to 15, so adding k to it leaves k datums per row.

Unpacker: ch0_x is the first L1 datum read and ch1_x the last, inclusive. ch1_x past x_dim - 1 reads into the next tile and wraps into Src row 0.

INCADCZW

opcode 0x55 · Address counters

Increment Z and W counters. Adds each value to its counter; the CR copies are not touched. Fields as SETADCZW, without a mask (0 leaves a counter alone). A change takes effect at the next new address. W has no address-modifier increment, so this (or SETADC) is how W steps.

Packer (probed): ch1_z += n moves the L1 output by n * l1_z_stride and ch1_w by n * l1_w_stride. ch0_w += 1 steps the Dst read one tile, ch0_z += 4 steps it 4 faces. So INCADCZW(4, ch1_z=1, ch0_w=1) after a tile's Last PACR moves both the output address and the Dst tile, with one l1_dest_addr write for the whole run: 8 FP32 tiles packed exactly, at 55 cycles a tile as the end op of a template-1 MOP, 66 from a REPLAY, 172 pushed by the RISC.

Unpacker (probed with z_dim 1, 2 and 4): the L1 read position is base + (Z * x_dim * y_dim + W * x_dim * y_dim * z_dim) datums, so ch0_z += 1 steps one face and ch0_w += 1 one whole tile, and the two add. A REPLAY of STALLWAIT, UNPACR, INCADCZW(1, ch0_z=1) read 4 consecutive single-face tiles correctly.

opcode 0x56 · Address counters

Advance Z and W from their CR copies. As ADDRCRXY, fields as SETADCZW: for each counter whose mask bit is set, CR += value, then counter = CR; mask 0 does nothing (probed). PACR

opcode 0x41 · Unpack / pack / mover

Pack Dst into L1. Reads up to four 16-datum Dst rows, converts them and appends them to the L1 output. Formats, ReLU, edge masks, strides and the output address come from cfg.PACK.

Output address. Only the first PACR after a last (or after reset) computes it; the PACRs after it append. It is (l1_dest_addr + 1) * 16 + Y * l1_y_stride + Z * l1_z_stride + W * l1_w_stride, in bytes, with Y, Z, W the channel-1 counters and the strides multiples of 16 (probed for all three). Self-advance (probed, FP32 / BF16 / BFP8): write l1_dest_addr once, set l1_z_stride to the tile's size in L1, and give the tile's last PACR an address-modifier slot with ydst_clear and zdst_incr=1. Each tile then lands after the one before with no address rewrite, 26..30 cycles a tile cheaper when the PACRs come from a MOP. zdst_clear returns to the base. For the Dst side, either the slot also has ysrc_clear and zsrc_clear and a SETADC sets channel-0 W to the tile index before each tile, or it has ysrc_incr=4 in place of ysrc_clear and the Dst rows keep counting into the next tile with no instruction between tiles. INCADCZW after the last PACR does the same job in one instruction, stepping the output address and the Dst tile together, at 55 cycles a tile from a MOP against 50 for the address-modifier slot plus its SETADC. With converted output, do not change those counters or l1_dest_addr while a tile is being packed.

A non-last PACR can hold its output until the next PACR: a STALLWAIT on Wait.PACK0 after it may never finish. End every sequence with last. A RISC pushing PACRs back to back is stalled until the packer drains, so a pushed loop is bound by the push rate. Do not ZEROACC or SFPSTORE into rows within about 3 instructions after the PACR that reads them.

FPU overview

  • An 8-row Dst block an arithmetic instruction wrote cannot be read back by the FPU for 5 cycles (hardware stalls), so loop over at least 6 distinct blocks. The packer and the SFPU do not get that stall: STALLWAIT on Wait.MATH before PACR or SFPLOAD touches rows the FPU has just written.
  • A Dst row operand is added to cfg.THREAD.dst_offset and the Dst RWC. release frees Src banks to the unpackers once the instruction is done. addr_mod names one of the 8 slots of cfg.ADDR_MOD, whose increments are applied to the SrcA / SrcB / Dst RWCs and the fidelity phase afterwards; slot 0 is kept all-zero.

MVMUL

opcode 0x26 · FPU · latency 5

Matrix multiply-accumulate. Dst[8 x 16] += SrcB[8 x 16] @ SrcA[16 x 16]. A 32 x 32 tile product is a sequence of these. It always accumulates: ZEROACC the block first for a plain product.

Rows: SrcB is the 8 rows at RWC.SrcB & 0x38, SrcA the 16 rows at RWC.SrcA & 0x30. There is no Src row operand. Fidelity: each instruction multiplies at most 5 bits of SrcA by 7 bits of SrcB, chosen by the fidelity phase (the fidelity RWC plus THREAD.fidelity_phase; bit 0 picks the SrcA part, bit 1 the SrcB part). One pass per phase, 1 cycle each: phase 0 alone is the coarsest BF16 product, phases 0+1 are the usual choice, all four use every bit of both operands. Maximum error on random BF16 data in +-4 with 1 / 2 / 3 / 4 phases: 1.29 / 0.198 / 0.0088 / 0.0086 (probed). An SrcB of ones or small integers needs only phases 0+1. Summation: even with all phases the 16 products of a column are added aligned to the largest one, keeping about 12 bits below it. Terms of similar magnitude add exactly; terms 2^-8 .. 2^-11 of the largest can be off by up to 40%, and terms below about 2^-12 of it vanish (probed; the rounding rule is not modelled). Formats: the FPU works in the format the unpacker handed over with the SrcA bank, for both operands (probed for the elementwise ops). See cfg.MATH.srca_fmt.

SFPU overview

  • An LReg holds 32 lanes of 32 bits: 4 rows of 8, covering the even or the odd columns of 4 consecutive Dst rows. Register operands (a, b, c, src, dest, lreg) take isa.LReg numbers. Results are written only to L0..L7, and only in enabled lanes: a lane is enabled unless predication is on (SFPENCC) and its condition flag is clear.
  • A destination of 12..15 does not execute the instruction: it records the instruction word as SFPLOADMACRO template (destination - 12) instead. SFPCONFIG and SFPLOADMACRO are the exceptions.
  • One instruction per cycle. Only the MAD column (SFPMAD, SFPMUL, SFPADD, SFPMULI, SFPADDI, SFPMUL24, SFPLUT, SFPLUTFP32) has 2-cycle latency; SFPSWAP (all modes) and SFPSHFT2 (modes 2, 3, 4) hold the issue slot an extra cycle (the hardware stalls the next non-SFPNOP SFPU op).
  • The hardware stalls most RAW hazards after a 2-cycle producer; the ones it misses are listed on each instruction. WAW needs nothing: the later write wins. Measured on Blackhole A0 card 1 across 46 producers x 70 consumers (boop-docs/probes/model.py).
  • Register usage lines name operands by position: VD [7:4] (dest), VC [11:8] (src / c), VB [15:12] (b), VA [19:16] (a), mod [3:0] (mode); R is the [23:20] register (lreg) of SFPLOAD, SFPLOADI, SFPSTORE, SFPLUT, SFPLOADMACRO. "stall logic sees" = what the hardware waits on; a read it does not see is an undetected hazard.

SFPLOAD

Other

Baby RISC-V cores

Which core runs what

Every core (BRISC, NCRISC, TRISC0-2): RV32IM, Zba, Zbb, pack/brev8/grevi, Zaamo, the F and Zfh subsets, ebreak (pauses the core for the debugger). BRISC and NCRISC only: mret. TRISC2 only: the V subset; on the other cores vsetvli still returns a VL, but the first vector load, ALU op or store hangs the core until tt-smi -r. From tt-isa-documentation BabyRISCV/InstructionSet.md and a probe on a p150a (2026-11-14) that ran on every core.

Missing instructions

Unimplemented encodings are UndefinedBehavior, not a trap: fdiv, fsqrt, lr.w/sc.w, Zbs, Zbc, packh/zip/unzip, and in RVV vdiv/vdivu/vrem/vremu, vfdiv/vfrdiv, vfsqrt, vfrsqrt7, vfrec7. ecall is RV32I, but nothing handles the trap.

Floating point

rm (rounding mode) is encoded but ignored: always round to nearest even (fcvt.w.s 3.75 with rtz gives 4). fcsr exists; fflags and frm do not. Arithmetic and fused ops treat denormal inputs as zero and flush denormal results (probed). fmadd/fmsub/fnmsub/fnmadd are not IEEE fused: rounding sits between separate mul+add and a true FMA.

cfg0 (CSR 0x7C0)

Bit 30 makes the Zfh (.h) arithmetic BF16 instead of FP16 (bit 31: RTNE, else RTZ). fcvt.s.h/fcvt.h.s still convert as FP16 in that mode (0x3FC0 -> 0x77C00000, probed), so convert bf16 <-> f32 with a 16-bit shift; the vector vfwcvt.f.f.v does follow the mode, and RVV FP ops at SEW=16 follow it too.

Zaamo atomics

Local L1 only, not MMIO and not other tiles (use NoC atomics for those). The hardware ignores aq/rl and always runs them as aq+rl. No lr.w/sc.w. Probed: amoadd.w, amoswap.w, amoor.w, amomaxu.w.

Counters

cycle and instret are CSRs 0xC00 and 0xC02 (csrrs rd, csr, x0); time is not implemented.

RVV on TRISC2

VLEN = 128 bits, ELEN = 32: SEW is 8, 16 or 32; a vsetvli with e64 hung TRISC2. ta/ma are ignored (always undisturbed); there is no vill bit. Most ops carry a false dependency on vd, fractional LMUL behaves like LMUL>1, and LMUL>1 is split into micro-ops (camel-cdr's rvv-bench). Copying 4 KiB of L1 with vle32/vse32 at m8 took 1298 cycles against 3349 for an 8x-unrolled lw/sw loop; summing 1024 words, 1372 against 4092.

What hw/isa.py encodes

RV32IM only (plus fence). The extensions above (Zba, Zbb, Zbkb/grevi, Zaamo, F, Zfh, RVV) are not used by codegen, so their encoders were removed.
