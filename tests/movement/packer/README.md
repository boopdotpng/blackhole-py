# Packer movement kernels

Handwritten row-major proofs for packer movement:

- runtime-sized copies from any FP32 Dst tile (0 through 7), at a chosen
  16-element Dst row offset, into an arbitrary aligned L1 CB page;
- dense BF16 and F32 output, including one element, non-row-sized tails, half
  tiles, and full tiles;
- standalone partial ReLU and nonnegative-upper clamp kernels in both output
  formats; and
- deterministic round-to-nearest-even and seeded stochastic FP32-to-BF16
  format conversion.

No path tilizes, untilizes, transposes, or otherwise reorders the values. Dst
is the internal FP32 staging layout and the packer writes a dense row-major L1
result. A native `PACR` emits one contiguous 16-element register row. One MOP
runs the runtime number of complete rows and, when needed, a second
single-iteration MOP emits the 1..15-element tail. The generated kernel has
two literal MOP-run sites and no literal `PACR` instruction stream, regardless
of runtime N.

Partial hardware stores can clear padding through the end of their final
16-element row (at most 64 output bytes); the tests verify that padding is zero
and that the sentinel immediately after it is unchanged. Dst offsets are
therefore row-aligned, while N itself is arbitrary. Stochastic rounding uses
the hardware gasket and packer enable bits and seeds the shared PRNG once from
the math thread; its 600-`SFPNOP` initialization delay is itself generated by
a MOP instead of hundreds of emitted instructions.

## Contiguous versus scattered Dst

```sh
PYTHONPATH=. pytest -q -s tests/movement/packer/test_scatter.py \
  --bh-hardware --bh-device=0 --bh-core=27
```

This benchmark unpacks BF16-exact FP32 values directly into Dst before timing.
It packs four 128-element logical blocks into one dense 512-element BF16 L1
buffer, then issues one acknowledged 1024-byte DRAM write and checks every
output value. A sentinel after the L1 output checks for over-writes.

Every case has the same 32 row PACRs in Replay. The contiguous baseline plays
them with one Replay instruction. Split cases use four eight-instruction
Replay segments, replace the input Y/Z/W counters between segments, and
conservatively drain PACK0 at each boundary. Only the final PACR closes the
output. The split-contiguous control isolates this segmentation overhead from
the distance between source slots. This is a measured lowering strategy, not
a hardware lower bound on scatter cost.

Packer configuration, input initialization, and an initial warmup are outside
the timing. Pack timing includes output-pointer reset, source addressing,
Replay issue, completion drains, and the RISC loop overhead. Each sample
contains 32 packs; results report the median of five samples in cycles per
512-element pack. The final DRAM write is timed separately, from command
submission through acknowledgement, excluding command configuration. This is
not an overlapped pack/NoC throughput measurement.

Device 0, worker 27 sample:

| Dst logical slots | Pack cycles | DRAM write cycles |
| --- | ---: | ---: |
| 0, 1, 2, 3 (one sequence) | 103.2 | 352 |
| 0, 1, 2, 3 (split control) | 134.2 | 352 |
| 0, 2, 4, 6 | 134.2 | 352 |
| 0, 4, 8, 12 | 134.2 | 352 |
| 0, 8, 16, 24 | 134.9 | 352 |
| 0, 16, 32, 48 | 134.1 | 352 |
| 0, 21, 42, 63 | 134.1 | 352 |

All outputs matched exactly. In that conservative version, splitting costs
about 30% in pack latency; distance itself has no appreciable additional cost.
FP32 slots are logical eight-row regions; the packer handles the physical
high/low-half mapping.

The benchmark now also compares two versions without intermediate drains:

- `queued`: retain the three Y/Z/W counter updates per segment.
- `one counter`: keep Z/W zero and select the absolute logical source row
  using Y alone, with one counter update per segment.

Both retain the final completion wait and output flush. PACR computes its
input address when it starts and blocks the issuing thread until work is
accepted; the next source counter update need not wait for the earlier
segment's output to reach L1. This reasoning applies to these ADC updates,
not arbitrary configuration-register changes while packing is in flight.

The one-sequence contiguous baseline remained 103.2 cycles. Optimizing the
scatter sequence reduced its overhead to roughly 2–3%, with no meaningful
growth as the gap increased. All these cases use only packer interface 0;
using multiple read interfaces is a separate optimization. These numbers
include the common per-pack setup/drain costs described above, and are not
isolated packer-throughput measurements.

### Blackhole configuration and further optimizations

Correction to the initial interpretation: Blackhole LLK's `cpack_common.h`
declares `NUM_PACKERS = 1`, configures section 0, and uses PACR's
`ReadIntfSel` to select read interfaces. The Wormhole description of four
independently configured packers must not be assumed to describe this path.
Blackhole `llk_pack.h` uses all read interfaces with a four-row source-counter
increment for ordinary full-height faces.

Two additional tests cover optimizations:

- `test_pack_reused_output_address_to_dram` programs the fixed output address
  once, outside timing. Every final PACR still closes the output, so the next
  pack starts again at the configured address. This applies to reused scratch
  output; it does not measure advancement through a real CB ring.
- `test_pack_four_read_interfaces_to_dram` additionally sets `ReadIntfSel=15`
  and advances source Y by four per PACR. Eight PACRs pack 512 elements; each
  scattered 128-element block uses two PACRs. The interfaces read four
  consecutive rows of the selected block, rather than four arbitrary blocks.
